NGINX Explained Like a Restaurant

Nov 17, 2026

NGINX is on almost every server I touch. But the config files looked like magic to me for a long time. What finally made it click was thinking of NGINX as the front desk of a restaurant.

So that's how this post works. Every NGINX job gets a restaurant picture first, then a small animation, then the real config.

The Restaurant

Keep this picture in your head for the rest of the post:

RestaurantWeb server
CustomerBrowser (the user)
Host at the front deskNGINX
KitchenYour app (Node.js, PHP, Python...)
Water and bread at the counterStatic files (HTML, CSS, images)
Several chefsSeveral app servers (load balancing)
Checking the reservation at the doorHTTPS and security
Soup kept warm at the counterCaching

Customers never walk into the kitchen. They talk to the host, and the host decides what happens next. That's NGINX in one sentence.

Why NGINX Is So Fast

Picture two restaurants. In the first one, every table gets its own waiter. The waiter takes the order, then just stands there waiting for the food. Ten tables, ten waiters, mostly standing around. That's how older web servers worked: one worker per connection.

In the second restaurant, one waiter handles all the tables. While one table's food is cooking, the waiter moves on to the next table. Nobody stands still. That's NGINX.

In real life, NGINX starts one worker per CPU core (worker_processes auto;), and each worker can handle thousands of connections at once. That's why a small $5 server running NGINX can handle a lot of traffic.

Job 1: Serving Static Files

If a customer asks for water, the host doesn't bother the kitchen. The water is right there at the counter, so the host just hands it over.

Static files are the water. HTML, CSS, JavaScript and images are already sitting on the disk, so NGINX sends them straight away. Only real "cooking" (like /api/users) goes to your app.

Browsercustomer
NGINXhost
/logo.png
Diskcounter
/api/users
Appkitchen

Files go straight from disk. Only API requests reach the app.

Example:

server {
    listen 80;
    server_name example.com;

    root /var/www/example;     # where the files live
    index index.html;

    location / {
        try_files $uri $uri/ =404;
    }
}

try_files means: look for the exact file, then a folder with that name, and if neither exists, return 404.

Job 2: Reverse Proxy

When a customer orders food, the host takes the order to the kitchen, waits for the plate and brings it back. The customer never sees the kitchen.

That's a reverse proxy. Your Node app runs on localhost:3000, hidden from the internet. NGINX sits in front on port 80/443, passes the request to the app and returns the answer.

Browsercustomer
NGINX:443 · host
Node app:3000 · kitchen

● request goes in, ○ response comes back. The app is never exposed.

Example:

server {
    listen 80;
    server_name example.com;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

The proxy_set_header lines pass along who the real customer is. Without them, your app thinks every request comes from 127.0.0.1 (NGINX itself).

You can mix both jobs. Files from disk, API to the app:

location /api/ {
    proxy_pass http://127.0.0.1:3000;
}

location / {
    root /var/www/example;
    try_files $uri /index.html;
}

Job 3: Load Balancing

On a busy night, one chef isn't enough. So the restaurant hires three, and the host gives the orders out in turn: first order to chef 1, next to chef 2, next to chef 3, then back to chef 1.

Userscustomers
NGINXhost
App 1chef 1
App 2chef 2
App 3chef 3

Round robin: each request goes to the next server in line.

Example:

upstream app_servers {
    server 10.0.0.11:3000;
    server 10.0.0.12:3000;
    server 10.0.0.13:3000;
}

server {
    listen 80;
    server_name example.com;

    location / {
        proxy_pass http://app_servers;
    }
}

Round robin is the default. You can change how NGINX picks a server:

  • least_conn; sends the order to the chef with the fewest orders right now.
  • ip_hash; always sends the same customer to the same chef. Useful when login sessions are stored on one server.

If one server dies, NGINX notices the failed requests and stops sending orders to it for a while. The restaurant keeps running.

NGINXhost

App 2✕ down
App 3chef 3

App 2 is down, so NGINX skips it. Users don't notice.

Job 4: HTTPS

The host checks reservations at the door so the kitchen doesn't have to. In the same way, NGINX handles HTTPS: it does the encryption work, then talks to your app over plain HTTP inside the server. This is called SSL termination.

Browsercustomer
NGINXdecrypts · host
Appkitchen

Encrypted on the internet (green), plain HTTP inside your own server.

The easiest way to get a free certificate is Certbot:

Command:

sudo apt install certbot python3-certbot-nginx
sudo certbot --nginx -d example.com -d www.example.com

Certbot edits your NGINX config for you and renews the certificate automatically. To send everyone from http to https:

Example:

server {
    listen 80;
    server_name example.com www.example.com;
    return 301 https://$host$request_uri;
}

Job 5: Caching

If everyone orders the same soup, a smart host keeps a few bowls warm at the counter. The first customer waits for the kitchen. Everyone after that gets a bowl right away, and the kitchen can rest.

NGINX can do the same. It saves the app's answer for a while and sends that copy to the next people who ask.

1st visit: cooked in the kitchen

Browsercustomer
NGINXsaves a copy
Appkitchen

2nd visit: served from the counter

Browsercustomer
NGINXfrom cache
Appresting

The second answer never touches the app, so it's much faster.

Example:

# inside the http { } block
proxy_cache_path /var/cache/nginx keys_zone=my_cache:10m max_size=1g inactive=60m;

server {
    location / {
        proxy_cache my_cache;
        proxy_cache_valid 200 10m;        # keep good answers for 10 minutes
        add_header X-Cache-Status $upstream_cache_status;
        proxy_pass http://127.0.0.1:3000;
    }
}

The X-Cache-Status header shows HIT or MISS, so you can check it with curl -I. Don't cache pages that are different for each user, like a dashboard or a cart.

How the Config Is Organized

Here's a second picture that helps with reading config files. Think of it as an apartment building:

  • http { } is the building. Settings here apply to everything.
  • server { } is one apartment, usually one website. server_name is the name on the door.
  • location { } is a room inside the apartment, one URL path like /api/ or /images/.
http {                              # building
    server {                        # apartment: example.com
        server_name example.com;
        location /      { ... }     # room
        location /api/  { ... }     # room
    }
    server {                        # apartment: blog.example.com
        server_name blog.example.com;
        location /      { ... }
    }
}

Where the Files Live

On Ubuntu and Debian:

PathWhat it is
/etc/nginx/nginx.confMain config. You rarely touch it.
/etc/nginx/sites-available/One file per website. Write your configs here.
/etc/nginx/sites-enabled/Links to the sites that are turned on.
/var/www/Website files.
/var/log/nginx/access.log and error.log.

To turn a site on, you link it from available to enabled. It's the same ln -s from my Linux commands post. On RHEL or Rocky, configs go in /etc/nginx/conf.d/ instead.

Commands You'll Use Every Time

After every config change, test first, then reload. Never skip the test.

Command:

sudo nginx -t                    # check the config for mistakes
sudo systemctl reload nginx      # apply changes, no downtime

sudo ln -s /etc/nginx/sites-available/example /etc/nginx/sites-enabled/
sudo systemctl status nginx      # is it running?
sudo tail -f /var/log/nginx/error.log

reload is better than restart. The host learns the new rules without kicking out the customers already inside.

Common Errors

These are the ones you'll see most, in restaurant words. Here's the most common one first:

Browsercustomer
NGINXhost
App✕ closed

The app isn't running, so NGINX has nothing to pass the order to: 502 Bad Gateway.

ErrorRestaurantWhat to check
502 Bad GatewayThe kitchen is closed.Your app isn't running, or it's on a different port than proxy_pass.
504 Gateway TimeoutThe kitchen is too slow.The app is stuck or a database query takes too long.
403 ForbiddenThe host isn't allowed into the storeroom.File permissions. NGINX runs as www-data, so check with ls -l.
404 Not FoundThat dish isn't on the menu.Wrong root path, or the file isn't there.
413 Request Entity Too LargeThe delivery won't fit through the door.Upload is too big. Raise client_max_body_size (default is 1M).

For any of them, the error log usually tells you exactly what went wrong:

sudo tail -n 50 /var/log/nginx/error.log
