What Is NGINX? Explained Like a Restaurant

Nov 17, 2026 · by Rezwan Hossain

Examples written for Ubuntu 24.04 and NGINX 1.24

NGINX (say "engine-x") is the program that sits in front of most websites. It answers visitors, hands out files, passes requests to your app, spreads traffic across servers and handles HTTPS.

I use it on almost every server I touch, but the config files looked like magic to me for a long time. What made it click was picturing NGINX as the host at a restaurant's front desk.

By the end of this post you'll know what NGINX does, be able to read a config file and put a site online with HTTPS. Every idea gets a restaurant picture, a small animation and a config you can copy.

What Is NGINX?

NGINX is a web server. It listens for visitors on ports 80 (HTTP) and 443 (HTTPS) and decides what to send back. That one program can do five jobs:

  • send files like HTML, CSS and images (a web server)
  • pass requests to your app and return its answer (a reverse proxy)
  • share traffic between several app servers (a load balancer)
  • handle HTTPS so your app doesn't have to
  • keep copies of answers to serve them faster (a cache)

NGINX vs Apache

Apache is the other big web server, and both are good. The practical differences:

NGINX Apache
Used for Reverse proxy in front of apps, static files Classic PHP sites, shared hosting
Config One central config. No .htaccess files. Central config plus .htaccess in each folder
Speed Event-based from the start Several modes. The modern "event" mode is event-based too.

If you're putting a Node, Python or Go app online, NGINX in front of it is the usual choice.

Words You'll See

Word Meaning
port A numbered door on a server. Web traffic uses 80 (HTTP) and 443 (HTTPS). Your app might use 3000.
localhost / 127.0.0.1 "This same machine." Only programs on the server itself can reach it.
header A small label sent with every request or response, like Host: example.com.
upstream The server NGINX passes requests to: your app.
301 A "moved permanently" answer that sends the browser to a new address.
$uri, $host Variables NGINX fills in for each request: the path asked for, and the domain name.

Where the Files Live

On Ubuntu and Debian:

Path What it is
/etc/nginx/nginx.conf Main config. You rarely touch it.
/etc/nginx/sites-available/ One file per website. Write your configs here.
/etc/nginx/sites-enabled/ Links to the sites that are turned on.
/var/www/ Website files.
/var/log/nginx/ access.log and error.log.

To turn a site on, you link it from available to enabled with ln -s (see my Linux commands post). On RHEL, Rocky, or NGINX installed from nginx.org's own packages, site configs go in /etc/nginx/conf.d/ instead.

How a Config Is Organized

Here's a second picture that helps with reading config files. Think of it as an apartment building:

  • http { } is the building. Settings here apply to everything.
  • server { } is one apartment, usually one website. server_name is the name on the door.
  • location { } is a room inside the apartment, one URL path like /api/ or /images/. 
http {                              # building (in nginx.conf)
    server {                        # apartment: example.com
        server_name example.com;
        location /      { ... }     # room
        location /api/  { ... }     # room
    }
    server {                        # apartment: blog.example.com
        server_name blog.example.com;
        location /      { ... }
    }
}

On Ubuntu, nginx.conf already has the http { } block and pulls in every file from sites-enabled/. So your site file starts at server { }.

How NGINX Picks a Location

When a request comes in, NGINX picks one room like this:

Type Example Rule
Exact location = /health Only that exact path. Wins straight away.
Prefix location /api/ Any path starting with it. The longest match is remembered.
Regex location ~ \.php$ Checked after prefixes, in order. The first match wins over the prefix.
Prefix, no regex location ^~ /images/ Like prefix, but if it's the longest match, regex is skipped.

Most configs only need plain prefixes. Just remember: the longest matching prefix wins, unless a regex also matches.

Your First Site in 5 Steps

Before the theory, let's get a page online. On a fresh Ubuntu server:

1. Install NGINX and open the firewall

sudo apt update
sudo apt install nginx
sudo ufw allow 'Nginx Full'      # opens ports 80 and 443

Open http://YOUR_SERVER_IP in a browser. You should see "Welcome to nginx!".

2. Add your files

sudo mkdir -p /var/www/example
echo "Hello from NGINX" | sudo tee /var/www/example/index.html

3. Write the site config in /etc/nginx/sites-available/example: 

server {
    listen 80;
    server_name example.com www.example.com;
    root /var/www/example;
    index index.html;
}

4. Turn it on, and turn off the default site

sudo ln -s /etc/nginx/sites-available/example /etc/nginx/sites-enabled/
sudo rm /etc/nginx/sites-enabled/default

The default site answers any request that doesn't match another server_name. If you skip removing it, you might keep seeing the welcome page and wonder why your site isn't showing.

5. Test and reload

sudo nginx -t
sudo systemctl reload nginx
curl -I http://example.com       # should say 200 OK

For example.com to reach your server, its DNS A record must point to the server's IP. If that part is new to you, my DNS post explains A records.

Why Is NGINX So Fast?

NGINX can keep thousands of visitors connected at the same time on a small server, and still use very little memory. People sometimes talk about it like it's magic. It isn't. It comes down to four design choices:

  1. Event-driven: react to what's ready, don't babysit connections
  2. Non-blocking: never sit and wait
  3. Low memory per connection
  4. One master, several workers: use every CPU core

Let's go back to the restaurant to see each one.

The Big Picture: Manager, Waiters and a Notice Board

When NGINX starts, it doesn't create one process. It creates a small team:

  • The master process is the manager. It reads the config, opens ports 80 and 443, and hires or replaces workers. It never serves customers itself.
  • Worker processes are the waiters. They talk to visitors, send files and pass orders to your app.
  • Shared memory is the notice board in the back. Every waiter can read it. NGINX keeps things like the list of cached pages and rate-limit counters there, so all workers see the same numbers.

A visitor's request lands on one of the workers. The surprising part is how many visitors one worker looks after at the same time. That's where the speed comes from.

Each worker runs an event loop (the spinning ring) and serves many connections (the lights).

1. Event-Driven: One Waiter, Many Tables

Picture a restaurant where every table gets its own waiter. You sit down, order, and your waiter stands next to your table until the food arrives. Now picture 1,000 tables. That's 1,000 waiters on the payroll, and almost all of them are just standing there.

That's how process-per-connection servers work, like Apache's classic "prefork" mode. Every visitor gets a dedicated worker, even while nothing is happening on that connection.

NGINX hires a smarter waiter. One waiter looks after a whole section of tables, and only walks over when someone raises a hand. The waiter doesn't check each table over and over. The tables signal when they need something.

The waiter only moves when a hand goes up. No standing around.

In computer terms, the "raised hand" is a message from the operating system: "this connection has something ready". On Linux, NGINX gets these messages through a feature called epoll.

How it works, step by step:

  1. A worker has many connections open at once.
  2. The operating system tells it which ones have something new, like a request that just arrived.
  3. The worker handles that bit of work.
  4. It goes back to its loop and picks up the next ready connection.

Why this makes NGINX fast

NGINX doesn't need a new process or thread for every visitor. One worker reacts only to connections that actually need attention, so it can look after thousands of them.

2. Non-Blocking: Never Stand and Wait

A customer orders soup, and the kitchen needs five minutes to make it. Should the waiter stand next to that table for five minutes?

Of course not. A good waiter tells the kitchen, goes to serve other tables, and comes back when the soup is ready.

NGINX works the same way. Some steps involve waiting: for your app to answer, or for a slow visitor's network to accept more data. When a worker hits one of these, it doesn't freeze. It moves on to other ready work and comes back when the data is there.

Blocking

  1. Request A starts
  2. The worker waits for A…
  3. B and C wait in line
  4. A finishes, then B, then C

Non-blocking

  1. Request A starts, then waits for data
  2. Meanwhile, the worker handles B
  3. …and C
  4. A's data arrives, and the worker finishes A
Blocking
A waiting for the app… A B C ✓ done
Non-blocking
A B C A ✓ done

Same three jobs. The non-blocking worker fills A's waiting time with B and C, so everything finishes sooner.

Why this makes NGINX fast

The worker spends its time doing work instead of waiting for it. Waiting time on one request becomes working time for other requests.

3. Low Memory: No Extra Staff per Customer

If every new customer needs a new waiter, a busy evening gets expensive fast: more salaries, more space, more people for the manager to keep track of.

Servers have the same problem. Every extra process or thread needs its own memory, and the operating system has to keep switching the CPU between them (called context switching). With thousands of visitors, that overhead adds up.

NGINX keeps a small, fixed team of workers. A new visitor only adds a little bookkeeping to a worker that's already running, not a whole new worker.

One thread per connection
NGINX

Connections keep arriving (squares). One memory bar climbs with them, the other barely moves.

What you get from that:

  • far less memory per connection
  • less time lost switching between threads
  • many more visitors on the same hardware
  • predictable memory use, even during a traffic spike

Why this makes NGINX fast

A thousand connected visitors doesn't mean a thousand threads. Memory stays low and steady, so the server has room left for real work.

4. One Master, Several Workers: Use Every CPU Core

One smart waiter is great, but there's a limit to what one person can carry. So the manager hires a few waiters and gives each one their own section of the restaurant.

A CPU core can only run one thing at a time. If your server has 4 cores, NGINX can run 4 workers, one per core, so no core sits idle. You rarely need to count them yourself. This one line, already in Ubuntu's nginx.conf, does it for you: 

worker_processes auto;    # one worker per CPU core

Each worker has its own event loop and handles many connections: 768 by default on Ubuntu (worker_connections), and you can raise that into the thousands.

Why this makes NGINX fast

Several workers run side by side, one per core, so NGINX uses all the CPU power you're paying for.

Bonus: Reloading Without Kicking Anyone Out

Imagine changing the menu in the middle of dinner. A bad manager throws everyone out, prints new menus and reopens. A good manager gives the new menu to fresh waiters, and lets the current waiters finish with their tables before they go home.

That's exactly what happens when you run:

sudo systemctl reload nginx
  1. The master reads the new config.
  2. It starts new workers with the new settings.
  3. The old workers stop taking new visitors and finish the ones they have.
  4. When they're done, they quit.

This is called a graceful reload. Visitors don't see an error page while you change settings. If the new config has a mistake, the master keeps the old workers running, which is one more reason to run sudo nginx -t first.

Job 1: Serving Static Files

If a customer asks for water, the host doesn't bother the kitchen. The water is right there at the counter, so the host just hands it over.

Static files are the water. HTML, CSS, JavaScript and images are already sitting on the disk, so NGINX sends them straight away. Only real "cooking" (like /api/users) goes to your app.

Browsercustomer
NGINXhost
/logo.png
Diskcounter
/api/users
Appkitchen

Files go straight from disk. Only API requests reach the app.

Example:

server {
    listen 80;
    server_name example.com;

    root /var/www/example;     # where the files live
    index index.html;

    location / {
        try_files $uri $uri/ =404;
    }
}

try_files means: look for the exact file, then a folder with that name, and if neither exists, return 404.

Make Files Load Faster

Two small additions help a lot: compress text files, and tell browsers to keep images and CSS for a while. 

# gzip: Ubuntu's nginx.conf already has "gzip on;", add the types
gzip_types text/css application/javascript application/json image/svg+xml;

# inside your server { }: browsers keep these files for 30 days
location ~* \.(css|js|png|jpg|svg|woff2)$ {
    expires 30d;
}

Job 2: Reverse Proxy

When a customer orders food, the host takes the order to the kitchen, waits for the plate and brings it back. The customer only ever talks to the host.

That's a reverse proxy. Your Node app runs on port 3000. NGINX sits in front on port 80, passes the request to the app and returns the answer.

Browsercustomer
NGINX:80 · host
Node app:3000 · kitchen

● request goes in, ○ response comes back. Visitors only talk to NGINX.

Example:

server {
    listen 80;
    server_name example.com;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

Keep the Kitchen Door Closed

NGINX in front doesn't hide your app by itself. Many apps listen on every network address by default, so port 3000 is still reachable from the internet. Tell the app to listen only on this machine: 

// Node.js / Express
app.listen(3000, '127.0.0.1');

Or block the port in the firewall. Without one of these, people can skip NGINX entirely.

Passing the Real Visitor IP

Your app sees every request coming from 127.0.0.1, because NGINX is the one connecting to it. The proxy_set_header lines attach the real visitor's IP and the original protocol as headers. Your app still has to be told to read them. In Express that's: 

app.set('trust proxy', 1);

Files From Disk, API to the App

You can mix both jobs in one site:

location /api/ {
    proxy_pass http://127.0.0.1:3000;
}

location / {
    root /var/www/example;
    try_files $uri /index.html;
}

Notice /index.html instead of =404 this time. Any unknown path gets the main page, which is what single page apps (React, Vue) need so their own router can show the right page.

Job 3: Load Balancing

On a busy night, one chef isn't enough. So the restaurant hires three, and the host gives the orders out in turn: first order to chef 1, next to chef 2, next to chef 3, then back to chef 1.

Userscustomers
NGINXhost
App 1chef 1
App 2chef 2
App 3chef 3

Round robin: each request goes to the next server in line.

Example:

upstream app_servers {
    server 10.0.0.11:3000;
    server 10.0.0.12:3000;
    server 10.0.0.13:3000;
}

server {
    listen 80;
    server_name example.com;

    location / {
        proxy_pass http://app_servers;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

Choosing a Method

Round robin is the default. Add one line inside upstream { } to change it:

  • least_conn; sends the order to the chef with the fewest orders right now.
  • ip_hash; always sends the same customer to the same chef. Useful when login sessions are stored on one server.

When a Server Goes Down

If a request to one server fails, NGINX tries the next server, and stops sending orders to the broken one for a while (10 seconds by default, set with max_fails and fail_timeout). The restaurant keeps running.

Userscustomers
NGINXhost
App 1chef 1
App 2✕ down
App 3chef 3

App 2 is down, so NGINX skips it and keeps serving from the others.

Job 4: HTTPS

Imagine every order travels in a sealed envelope. Nobody on the way can read it or change it, and the restaurant's stamp proves it's the real restaurant. The host opens the envelope at the front desk, so the kitchen doesn't have to.

That's HTTPS with NGINX. The connection from the browser is encrypted and the certificate proves your site is really yours. NGINX decrypts it and talks to your app over plain HTTP inside the server. This is called SSL termination.

Browsercustomer
NGINXdecrypts · host
Appkitchen

Encrypted on the internet (green), plain HTTP inside your own server.

Before You Run Certbot

Certbot gets free certificates from Let's Encrypt. It will fail unless:

  • your domain's DNS A record points to this server's IP
  • port 80 is open, because Let's Encrypt checks your site over HTTP first
  • NGINX already has a server_name for the domain (step 3 above)

Command:

sudo apt install certbot python3-certbot-nginx
sudo certbot --nginx -d example.com -d www.example.com

This installs Certbot from Ubuntu's packages. The Certbot site at certbot.eff.org shows the recommended way for your exact system.

What Certbot Changes

Certbot edits your site file and adds lines marked # managed by Certbot, roughly like this: 

server {
    listen 443 ssl;
    server_name example.com www.example.com;
    root /var/www/example;

    ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;
    include /etc/letsencrypt/options-ssl-nginx.conf;
}

server {
    listen 80;
    server_name example.com www.example.com;
    return 301 https://$host$request_uri;
}

The second block sends everyone from http to https. Certbot usually adds it for you, so check before writing your own. Two blocks for the same name and port give a "conflicting server name" warning.

Certificates renew automatically. To check that renewal works:

sudo certbot renew --dry-run

Job 5: Caching

If everyone orders the same soup, a smart host keeps a few bowls warm at the counter. The first customer waits for the kitchen. Everyone after that gets a bowl right away, and the kitchen can rest.

NGINX can do the same. It saves the app's answer for a while and sends that copy to the next people who ask.

1st visit: cooked in the kitchen

Browsercustomer
NGINXsaves a copy
Appkitchen

2nd visit: served from the counter

Browsercustomer
NGINXfrom cache
Appresting

The second answer never touches the app, so it's much faster.

Example:

# in /etc/nginx/nginx.conf, inside the http { } block
proxy_cache_path /var/cache/nginx keys_zone=my_cache:10m max_size=1g inactive=60m;

# in your site file
server {
    listen 80;
    server_name example.com;

    location / {
        proxy_cache my_cache;
        proxy_cache_valid 200 10m;        # keep good answers for 10 minutes
        add_header X-Cache-Status $upstream_cache_status;
        proxy_pass http://127.0.0.1:3000;
    }
}

The X-Cache-Status header shows HIT or MISS, so you can check it with curl -I. Don't cache pages that are different for each user, like a dashboard or a cart.

Why You Might Always See MISS

NGINX plays it safe. By default it won't cache an answer if:

  • the app sends a cookie with it (Set-Cookie)
  • the app says not to (Cache-Control: private, no-cache or no-store)
  • the request isn't a GET or HEAD

Many frameworks add a session cookie to every page. If you always see MISS, check the response headers with curl -I first.

Basic Security

Every restaurant needs a bouncer at the door. These are three easy rules to add:

Don't show your NGINX version (in the http { } block): 

server_tokens off;

Slow down people hammering your login page:

# http { } block: 5 requests per minute per visitor IP
limit_req_zone $binary_remote_addr zone=login:10m rate=5r/m;

# your site file
location /login {
    limit_req zone=login burst=5;
    proxy_pass http://127.0.0.1:3000;
}

Add a few safety headers (inside server { }): 

add_header X-Content-Type-Options "nosniff";
add_header X-Frame-Options "SAMEORIGIN";
add_header Referrer-Policy "strict-origin-when-cross-origin";

One gotcha: if a location { } has its own add_header, it drops all the headers from the server { } level. Repeat them there if you need to.

Commands You'll Use Every Time

After every config change, test first, then reload. Never skip the test.

Command:

sudo nginx -t                    # check the config for mistakes
sudo systemctl reload nginx      # apply changes, no downtime

sudo nginx -T                    # print the full config NGINX is using
sudo systemctl status nginx      # is it running?
sudo tail -f /var/log/nginx/error.log

reload is better than restart. The host learns the new rules without kicking out the customers already inside.

Common Errors

These are the ones you'll see most, in restaurant words. Here's the most common one first:

Browsercustomer
NGINXhost
App✕ closed

The app isn't running, so NGINX has nothing to pass the order to: 502 Bad Gateway.

Error Restaurant What to check
502 Bad Gateway The kitchen is closed. Your app isn't running, or it's on a different port than proxy_pass. On RHEL, SELinux can block it: setsebool -P httpd_can_network_connect 1.
504 Gateway Timeout The kitchen is too slow. The app took longer than 60 seconds (proxy_read_timeout). Look for a stuck app or a slow database query.
403 Forbidden The host isn't allowed into the storeroom. File permissions (NGINX runs as www-data on Ubuntu, nginx on RHEL; check with ls -l), or the folder has no index.html.
404 Not Found That dish isn't on the menu. Wrong root path, or the file isn't there.
413 Request Entity Too Large The delivery won't fit through the door. Upload is too big. Raise client_max_body_size (default is 1M).

For any of them, the error log usually tells you exactly what went wrong: 

sudo tail -n 50 /var/log/nginx/error.log
